#### Informal Design Guidelines for Relation Schemas

![](../images/20261118_dbsystem_db12_03.png)

- Relational DB를 Design 한다는 것은 무슨 뜻일까
- 주어진 Application이 있을 때 이것을 위한 좋은 Table Schema를 잘 정의하는 것.
- Requirements Analysis를 하고 ER을 만들고, 그것을 Relation Design 하는 과정을 통해 Design 해야함.
- DB는 몇 개의 Table로 구성될 것인가?
- 각 Table에 포함되어야 할 Attribute는 무엇인가?
- 즉, Table을 Define하고 각 Table에 어떤 Attribute을 넣어야 하는가를 결정하는 것이 Relational Database Design임.

![](../images/20261118_dbsystem_db12_04.png)

- Table이 주어졌을 때 해당 Table의 Good / Bad을 판단할 수 있어야함.
  - Attribute의 의미적 측면
  - Tuple 내의 중복적인 내용 정도
  - NULL의 정도
  - 거짓 Tuple의 정도
- Formal Criteria
  - Normalization

#### Semantics of Attributes in Relations

![](../images/20261118_dbsystem_db12_05.png)

- Attribute의 의미적 측면에서 Relation을 평가하는 기준
- 주어진 Table Schema가 있을 때 Table의 Attribute들은 Real-World에서 상호 연관된 의미를 가져야 한다.
- STUDENT(name, age, gender, address) → Real-World에서 연관된 attribute만이 존재하니까 Good Relation이 됨.

![](../images/20261118_dbsystem_db12_06.png)

- 각 Relation과 Attribute들은 Real-World에서 관련있는 내용들만 존재함.

#### Guideline 1

![](../images/20261118_dbsystem_db12_07.png)

- Table에 속한 각각의 Tuple은 실제 Real-World에서 존재하는 하나의 Entity Instance이거나 하나의 Relationship Instance이어야 한다.

  → 2개 이상의 Entity Instance들에 대한 정보가 섞여 하나의 Tuple에 섞이는 것은 좋은 Table Schema가 아님.
- 2개 이상의 Entity Type 혹은 Relationship Type에 속하는 Attribute들을 섞어서 하나의 Table에 포함하는 것을 피해라.

![](../images/20261118_dbsystem_db12_08.png)

- 위 슬라이드에는 (a)에는 EMPLOYEE와 DEPARTMENT라는 2개의 Entity Instance이 섞여 있고 (b)에는 EMPLOYEE와 PROJECT라는 Entity Instance이 섞여 있음.

#### Update Anomalies

![](../images/20261118_dbsystem_db12_14.png)

- Update 시에 문제가 생겨서는 안된다.
- Update를 할 때 예상한 것과 다른 방식으로 작용해서는 안됨.
- Insertion, Deletion, Modification 등의 행위를 할 때 ㅇㅇ

![](../images/20261118_dbsystem_db12_15.png)

- Insertion Anomalies
  - Table에 한 tuple을 삽입하고 싶지만 삽입되지 않는 상황
  - EMP\_DEPT Table에 새롭게 추가되어 소속 Employee가 없는 Dept에 대한 Tuple을 추가하고 싶을 때 오류가 생김
  - 왜냐면 이 Table의 PRIMARY KEY는 EMP\_Ssn + DEPT\_Num이 되기 때문에 EMP\_Ssn이 NULL이 됨.
  - 이런 경우 DEPARTMENT와 EMPLOYEE를 분리해서 각각의 table을 가지고 있으면 됨.

![](../images/20261118_dbsystem_db12_16.png)

- Deletion Anomalies
  - 존재하는 tuple을 지우고 싶을 때 지우지 못하는 상황
  - EMP\_DEPT table에서 X라는 Department에 EMPLYOEE가 Y 한 사람만 남았을 때, Y와 관련된 tuple을 지울 수 없음  
    → X Dept에 오류가 생기기 때문

![](../images/20261118_dbsystem_db12_17.png)

- Modification Anomalies
  - Table에 존재하는 Tuple에 대한 정보를 수정하는 상황에 오류가 생긴 경우
  - EMP\_DEPT Table에 존재하는 X라는 Department의 mgr 정보를 수정하는 경우를 생각해보자.
  - X라는 Department에 속한 모든 EMP의 tuple을 수정해야 한다.
- EMP\_DEPT를 EMPLOYEE, DEPARTMENT로 나눠서 해결할 수 있음.

#### NULL Values in Tuples

![](../images/20261118_dbsystem_db12_19.png)

- Meanings of NULLs
  - Unknown value / Unavailable
  - Not applicable attribute

![](../images/20261118_dbsystem_db12_20.png)

- NULL은 의미가 존재하는 값이 아니다.
  - 저장 공간이 낭비됨
  - 애매모호한 의미를 가짐
  - Aggregate 함수를 적용하는 것에 있어 어려움이 존재함

    ex) Salary를 구하고 싶은데 NULL이 많다면 정확한 값 계산이 어려워짐

#### Guideline 3

![](../images/20261118_dbsystem_db12_21.png)

  - NULL이 되는 Tuple을 최소화하도록 설계

#### Functional Dependencies

![](../images/20261118_dbsystem_db12_28.png)

- 앞에서는 FORMAL 하기 보다 INFORMAL하게 좋은 DB Schema에 대해 감을 길렀다고 생각하면,
- FORMAL 하게 좋은 DB Schema에 대한 Normal Form에 대해 배우게 될 예정
- Functional Dependency란 Relational DB Schema가 주어졌을 때 Schema를 분석할 수 있는 Formal한 Tool임.

  → 주어진 Schema가 Normal Form이냐 아니냐를 판단.

![](../images/20261118_dbsystem_db12_29.png)

- Format : X → Y
  - X라는 Attribute이 Y라는 Attribute을 Functionally Determine한다.
  - X의 Value가 Y의 Value를 Functionally Determine한다.
  - Y의 Value가 X의 Value에 Functionally Dependent On 된다.
- 여기서 말하는 함수란 어떤 것과 어떤 것의 Mapping을 뜻하는 것.
  - X가 결정되면 Y의 값도 결정된다는 것.

![](../images/20261118_dbsystem_db12_30.png)

- X가 Y를 함수적으로 종속시킨다.

   = 주어진 Relation에 2개의 Tuple이 있을 때 그 Tuple의 X라는 Attribute value가 같다면, Y의 값도 같아야 한다.

  - 만약 Tuple 들이 X라는 attribute에 대해서 같은 값을 가진다면 Y라는 attributed에 대해서 같은 값을 가진다.
  - X라는 attribute의 값이 Y라는 attribute의 값을 UNIQUE하게 결정한다.
- Real-World의 예시로
  - Department → School  
    : 대학교에서 학생에 대한 Table이 있다고 가정해보자.  
    학생이라는 Table에서 Department(학과)는 School(단과대)를 종속적으로 결정한다.

    → 같은 학과 학생은 같은 단과대학에 속하니까 ㅇㅇ

  - City → Province  
    : 어떤 사람들이 살고 있는 City(시)가 같다면 Province(도)가 자동으로 결정된다.

![](../images/20261118_dbsystem_db12_31.png)

- 만약 어떤 Table R이 있고 X는 R의 Candidate Key라고 하자.
  - R에 존재하는 어떠한 attribute subset Y이든
  - X → Y를 만족한다.
  - 왜 그럴까?  
    → X는 Key이기 때문에 X가 같은 tuple은 존재하지 않음 ㅇㅇ  
    → 그렇기에 X가 같은 tuple이 유일하기에 당연히 Y가 자동 결정됨
- X → Y는 Y → X를 항상 만족시키지 않는다.

![](../images/20261118_dbsystem_db12_32.png)

- FD는 Table Schema R의 특징 중 하나이다.
  - Table Schema가 있고 FD가 있는게 아니라, FD가 존재하고 그걸 Table Schema에 enforce 하는 구조라는 말임.
  - 특정 instance r에만 적용되는 특이한 특징이 아니라는 것.

![](../images/20261118_dbsystem_db12_33.png)

- Ssn → Ename : 주민번호가 같으면 이름도 같다.
- Pnumber → \{Pname,Plocation\} : 프로젝트 number가 같으면 플젝 이름과 위치도 같다.
- \{Ssn, Pnumber\} → Hours : 이 Table 내에서 Ssn + Pnumber는 Candidate Key이자 Primary Key이기 때문에

#### Inference Rules for FDs

![](../images/20261118_dbsystem_db12_34.png)

- F : Table R에 대해서 정의되어 있는 FD들의 집합
- F+(closure of F) : 주어진 F으로부터 유추될 수 있는 모든 FD들의 집합

![](../images/20261118_dbsystem_db12_35.png)

- F 내에 2개의 FD가 정의되어 있을 때 F+에 대해 알아보자.
- Ssn → Dnumber → \{Dname, Dmgr\_ssn\}이니까 Ssn → \{Dname, Dmgr\_ssn\}
- Ssn → Ssn
- Dnumber → Dname
- 존재하는 FD에 대해 어떻게 inferr 할 것인가?

![](../images/20261118_dbsystem_db12_36.png)

- F를 통해 F+를 inferr하는 규칙이 어떻게 되는가?? → Armstrong’s inference rule

  1. Y가 X의 subset 이라면 X → Y 이다.
  2. X → Y라면, XZ → YZ이다.
  3. X → Y 이고 Y → Z 이면 X → Z이다.
- Sound and Complete  
  → SOUND : 위 3개의 rule을 통해서 infer된 FD는 항상 hold 된다.  
  → Complete : 위 3개의 rule을 반복적으로 적용하면 F+를 놓침없이 찾을 수 있다.

![](../images/20261118_dbsystem_db12_37.png)

- Armstrong을 제외한 나머지 rules

  4. X → YZ이면 X → Y, X → Z이다.
  5. X → Y, X → Z이면 X → YZ이다.
  6. X → Y, WY → Z이면 WX → Z이다.  
     : WX → WY니까 WX → Z이 가능.
- 4\~6은 Armstrong’s rules에 의해 증명 가능하다.
- 4\~6 없이도 F+를 전부 구할 수 있음.

#### Systematic Way to Determine Additional FDs

![](../images/20261118_dbsystem_db12_38.png)

- X : FD에서 left-hand side에 존재하는 Attribute의 집합
- X+ (Closure of X under F) : F에 근거한 X에 의해 Functionally determined 되는 Attribute의 집합.

![](../images/20261118_dbsystem_db12_39.png)

- X가 주어졌을 때 X+를 구하는 방법

  1. 주어진 X가 있다면 그 안의 Attribute을 X+에 넣는다.
  2. 후의 비교를 위해 oldX+에 X+를 복사함.
  3. FD인 Y → Z를 보았을 때 Y가 현재 가지고 있는 X+에 속한 원소라면 Z도 X+를 추가한다.
  4. 추가된 X+를 다시 oldX+에 복사
  5. 3번을 반복하여 X+를 점점 늘려간다고 생각하면 됨.

![](../images/20261118_dbsystem_db12_40.png)

- \{Ssn\} +을 구하는 과정을 생각해보자

  1. Ssn을 Ssn+에 추가
  2. Ssn → Ename을 통해 Ename을 Ssn+에 추가
