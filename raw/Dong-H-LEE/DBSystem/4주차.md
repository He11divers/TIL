#### Database Design Process

![](../images/20260923_dbsystem_week4_03.png)

- 왼쪽은 우리 강의 수준을 벗어남.
- 오른쪽 부분에 대해서 공부할거
- Miniworld
    - 한양대학교에 대한 DB를 만든다고 했을 때
    - RealWorld → 한양대
    - MiniWorld → 한양대를 운영하기 위해 필요한 Data
- REQUIREMENTS COLLECTION AND ANALYSIS
    - System Analyist가 담당
    - 실제 Database를 구축하기 위해서 어떤 Requirement가 있는가?
    - Data Requirements
- 그 이후 Database Design
    - USER 중 Database Designer가 담당

    - Database의 골격을 정하는 것

- Logical DESIGN 부터는 DBMS의 구조 등을 염두에 두고 진행해야함.

#### Entities and Attributes

![](../images/20260923_dbsystem_week4_09.png)

- Entity(개체)
    - 실세계에 독립적인 존재로서 존재하는 어떠한 것.
    - 사람, 차, 집, 학생, 직원 etc..
- Attributes(속성)
    - 어떠한 entity를 설명해주는 특정한 properties.
    - 이름, 나이, 주소, 직업, 번호, 년식 etc..
    - attribute value → 홍길동(이름이라는 attribute에 들어가는 value)

![](../images/20260923_dbsystem_week4_10.png)

#### Attributes의 Types

![](../images/20260923_dbsystem_week4_11.png)

- Simple(atomic) attirbutes
    - 더 나뉘어 질 수 없는 attributes
- Composite attributes
    - 작은 subpart로 나누어서 생각할 수 있는 attributes
    - 계층 구조로 형성할 수 있다. (subpart로 나눌 수 있으니까)
    - ex) 이름 → 성, 성을 제외한 이름

    ![](../images/20260923_dbsystem_week4_12.png)

![](../images/20260923_dbsystem_week4_13.png)

- Single-valued attributes
    - 특정 하나의 entity에 대해서 하나의 값만 들어갈 수 있음.
    - ex) 나이
- Multivalued attributes(set attributes)
    - 하나의 entity에 대해서 여러 값들이 들어갈 수 있음.
    - ex) 번호 → 투폰 쓰는 사람인 경우 두 번호 다 넣을 수 있도록 하는 것.

![](../images/20260923_dbsystem_week4_14.png)

- Stored attributes
    - 실제 database에 물리적으로 저장되는 것.
    - ex) 생년월
- Derived attributes
    - 실제 저장되어 있는 다른 attributes에서 유추해서 알려줄 수 있는 attributes
    - ex) 생년월일 attributes를 통해서 나이를 유추할 수 있음

#### Entity Type

![](../images/20260923_dbsystem_week4_15.png)

- Entity Type : 같은 attribute의 조합을 가지는 entity들의 집합
- ex) 홍길동 → entity / 사원 → entity type
- entity type은 schema에 해당, entity는 instance에 해당
- 사원이라는 entity type 안에 이름, 나이 등의 attribute가 존재한다.

![](../images/20260923_dbsystem_week4_16.png)

![](../images/20260923_dbsystem_week4_17.png)

- Domain
    - 어떤 특정한 attribute에 할당 될 수 있는 value들의 set
    - ex) 어떤 attribute A에 domain : attribute A에 할당될 수 있는 value들의 집합
    - ex) 어떤 직원의 age : 20\~70 사이의 값 → 이게 domain

#### Key Attribute

![](../images/20260923_dbsystem_week4_18.png)

![](../images/20260923_dbsystem_week4_19.png)

- 서로 다른 entity라면 같은 attribute에 대해 같은 value를 가질 수 없다.(고유성)
- Key attribute의 값은 각각의 entity를 유일하게 식별하는데에 사용 되는 attribute임.
- ex) 학번
- **여러 개의 attribute가 합쳐져서 하나의 key 역할을 할 수도 있음.**
- **하나의 entity type에 key가 여러 개 있을 수도 있음.**
- “key”는 현재 존재하는 entity set이 아닌 모든 entity set을 고려했을 때 항상 고유성을 만족할 수 있도록 해야함.

    → 특정 entity set에만 적용되는 key라는 것이 없음.

    → key로 선정이 되어 있다면 해당되는 entity type에 따르는 어떠한 entity set은 그것을 만족해야함.

![](../images/20260923_dbsystem_week4_20.png)

- Registration이라는 값이 key라면 number와 state라는 2개의 attribute가 key가 될 수도 있다. → 여러 개의 attribute가 합쳐져서 key 역할을 함.
- Registration과 Vehicle_id 둘 다 key 역할을 함.

#### Initial Conceptual Design of the COMPANY Database

![](../images/20260923_dbsystem_week4_21.png)

- Relation이라는 개념 없이 Attribute를 가지고 Database를 Design한 것
- Department
    - 자연어로 표현되어 있는 requirement가 있을 때 그걸 보고 여기처럼 entity type을 설계하는 것이  initial conceptual design
    - **NAME** → unique 해야함 → department entity에서 key 역할을 함.
    - **NUMBER** → unique → key
    - \{LOCATIONS\} → department 하나는 여러 위치에 존재할 수 있다. → multivalued attribute(하나의 값만 가지는게 아니라 여러 value를 가질 수 있다.)
- Project
    - **NAME** → 서로 다른 Project는 같은 NAME을 가질 수 없다.
    - **NUMBER** → 서로 다른 Project는 같은 Project Number를 가질 수 없다.
- Employee
    - NAME → Employee의 Name은 고유하지 않음(동명이인) → 단, 성 + 이름 , 이름, 성 처럼 여러 Value를 포함할 수 있음 → Composite Attribute
    - **SSN(Social Secrety Number)** → 사번 → key
    - \{WoksOn(Project, Hours)\} → 어떤 Project에서 얼마나 일했는지를 표현 → multivalued & composite attribute
- Dependent(부양가족)
    - **Employee** → 누구의 부양가족인가?
    - **DependentName** → 부양가족의 이름
    - 사실 Employee와 DependentName은 떨어져있는게 아닌 서로 연결되어 있는 attribute가 맞음
- E-R Model에서 initial design을 하면 이런 느낌으로 구성이 됨.

#### Concepts of Relationship

![](../images/20260923_dbsystem_week4_22.png)

- Relationship Instances
    - Entity Sets 내에 entity들 간의 연관성
- Relationship Type
    - Entity들 간의 연관성이 아니라 entity type 간의 관계의 집합(ex: 교수 - 학생)

#### Relationship Degree

![](../images/20260923_dbsystem_week4_24.png)

- 그 relationship type에 참여하는 entity type의 수
- ex) WORKS_FOR : WORKS_FOR라는 relationship type의 수는 ? → 참여하는 entity type의 수 → EMPLOYEE & DEPARTMENT → 2 → degree는 2
- Binary → degree가 2 → 대부분의 DB에서 Binary Relationship임

    ![](../images/20260923_dbsystem_week4_25.png)

- Ternary → degree가 3

    ![](../images/20260923_dbsystem_week4_26.png)

    - SUPPLY : SUPPLIER, PART, PROJECT 3개의 entity type이 참여하는 degree가 3인 relationship type

        ![](../images/20260923_dbsystem_week4_27.png)

        1. r1은 s1이라는 공급자가 p1을 j1이라는 project에 공급하는 것
        2. r3는 s1이 p2를 j1에 공급하는 것
- Ternary Relationship Type을 3개의 Binary Relationship Type으로 해결할 수는 없을까? → 표현할 수는 있지만 등가는 아니다. → 왜 그럴까? 생각해봐라.

#### Recursive Relationship

![](../images/20260923_dbsystem_week4_28.png)

![](../images/20260923_dbsystem_week4_29.png)

- Role Name
    - 참여하는 entity type이 각각의 relationship instance에서 어떤 역할을 하는지 명시한 것
    - ex) EMPLOYEE와 DEPARTMENT가 WORKS_FOR라는 relationship type에 참여한다면 각각 어떤 역할로 참여하고 있는가? → EMPLOYEE는 일꾼, DEPARTMENT은 일하는 위치
    - 하지만, 서로 다른 entity가 하나의 relationship type에 참여하는 경우에는 굳이 role name을 써주지 않아도 된다. → 어짜피 2개는 명확히 역할이 다르니까 → recursive relationship에서는 필요함!!
- Recursive Relationship Type
    - 그 relationship type에 하나의 entity type이 참여하는데 2번 이상 각각 다른 역할로 참여하는 relationship type
    - 이런 경우에는 각각의 역할에 role name을 정해줘야 헷갈리지 않음

![](../images/20260923_dbsystem_week4_30.png)

- r1이라는 instance는 e1(2)과 e5(1)를 연결해주는 instance
- r1은 e5가 상사(suvervision) e1이 부하직원임을 나타냄
- 이 RR은 binary임 → 2개의 entity를 엮고 있음
- EMPLOYEE라는 entity type이 2번 참여하는데 각각 부하(2), 상사(1)의 역할로 참여함
