#### Data Models → 나중에 집중적으로 배울 것임.

![](../images/dbsystem_week3_02.png)

- Data의 특성을 잘 표현하기 위한 것들이라고 생각하면 됨.
- Data Models : Database의 구조 또는 특성을 “표현”하기 위한 개념들의 모음.
    - Data types, Relations, Constraints 들의 구조로 이루어져 있음.
- Data 추상화를 가능하게 하기 위한 의미를 제공한다.
- Data Model은 구분할 때 concept의 level을 기준으로 크게 3가지로 구분한다.
    - “구분”에는 언제나 기준이 있어야함.
    - Physical Models, Conceptual Models, Representational Models

#### Physical Data Models

![](../images/dbsystem_week3_03.png)

- 여기서 말하는 물리적이란? →  Data가 하드디스크 등의 storage media 안에서 실제로 데이터가 어떤 형태로 저장되는가에 대한 의미를 가지고 있음.
- Physical Model을 통해서 Data를 표현하면 실제로 Data가 어떻게 저장되겠구나 라는 Detail을 알 수 있다. (어떤 Type인가?, Data Access를 위한 index, access path 등)

#### Conceptual Data Model

![](../images/dbsystem_week3_04.png)

- 일반 사용자들을 위해 저장되어야 하는 Data가 개념적으로 어떻게 표현되어야 하는지를 나타내는 model임. → physical에서 type 등의 표현은 전공자나 전문가에 익숙한 표현이다.
- Data를 사람들이 data를 인식하는 방법으로 표현한다(?) → 아무튼 일반인도 이해하기 쉽도록 표현해준다.
- 대표적인 예시 : E-R Model(Entity-Relationship Model)

#### Representational Data Models

![](../images/dbsystem_week3_05.png)

- Physical은 너무 low level, Conceptual은 너무 high level인데 representaitonal은 그 중간 Level의 model임.
- 즉, physical과 conceptual의 갭을 매꿔주는 model임
- data를 storage media에 저장하는 model(physical)과 비슷하기도 함.
- 사람이 이해하기 쉬우면서도 physical의 특성도 가지고 있음.
- 대부분의 상업적 DBMS는 이 model을 활용함
- oracle, sql server 등의 상용 DBMS에 가지고 있는 model은 representational model을 가지고 있는 것임.
- Implementation Data Models라고 부르기도 함.

#### Schemas and Instances

![](../images/dbsystem_week3_06.png)

Database Schema

- Data Model은 내 application이 다루는 Database의 구조를 나타내기 위해 사용한다.
- Database의 “구조”를 결정한 후 Data Model을 통해서 표현한다.
- 여기서 Data Model을 통해서 표현된 “구조”를 Database Schema(meta-data)라고 한다.
- 즉, Database 구조의 표현이다.
- intension이라고도 한다.
- Database Schema는 Database를 설계할 때 결정됨
    - Database Designer에 의해 design이 결정될 때
    - 그 구조는 Database의 life cycle 동안 거의 변하지 않음(절대 불변은 아님)

Schema diagram

- Schema의 여러 측면을 그림으로 표현한 것이 Schema Diagram임.

    ![](../images/dbsystem_week3_07.png)

    - University Database Schema Diagram의 예시라고 생각하셈.

![](../images/dbsystem_week3_08.png)

- Instance : 그 구조 하에 들어가는 사용자의 data
- Database Instance : 특정 시점(시간)에 실제 database에 저장되어 있는 Data를 말한다.

    → 왜 특정 시간이 필요할까? : 현재 시점의 database와 20초 후 새로운 data가 들어온 상황에서의 database의 instance는 다르기 때문이다.
- database state, snapshot, occurrence, extension이라고 부르기도 한다.
- data의 변경에 따라 자주 바뀜

> Schema는 자주 변하지 않지만, Instance는 자주 변한다.

#### Three-Schema Architecture

![](../images/dbsystem_week3_09.png)

- 3가지 database schema를 가지는 방식의 구조
- Application program을 database 구조에 종속되지 않도록 하기 위함.
- 즉, application이 database의 구조에 종속되지 않도록 하기 위해
- Database Designer
    - 어쨋든 schema니까 database의 schema를 결정하는 database designer에 의함.

    1. 수집한 Data 중 어떤 data를 database에 저장할 것인지 선택
    2. 해당 data를 저장할 database의 구조 및 특징을 정의

    > 즉, Database Designer는 database schema를 결정하는 역할

![](../images/dbsystem_week3_10.png)

- External / Conceptual / Internal 이렇게 3가지여서 three-schema
- Conceptual & Internal의 공통점 : application에서 다루는 전체 data에 대한 schema임.
- Conceptual Level : Internal이 너무 하위 level이라 사람이 보기 쉽게 하기 위해 만들어진 middle level이라고 생각하면 됨. → Conceptual data model or Representational Model로 표현됨
- Internal Level : Physical model로 표현되는 schema임.
- External View : 전체가 아닌 일부분을 나타냄 → 사용자가 바라보고 있는 일부 data에 대한 view를 보여주는 것 → Model은 Conceptual Schema에서 사용하는 model과 일치함.
- 사용 흐름
    - 사용자가 Query를 사용하여 원하는 External View(일부분)에 대한 요청을 보내면 DBMS는 그 요청이 Conceptual Schema(전체) 중에서 어떤 것인지를 판단한다.
    - 이후 External View(부분)에 대한 query를 Conceptual Schema(전체)에 대한 query로 바꾼다. → 이 행위를 External / Conceptual Mapping이라고 함.
    - 이후 Conceptual에 대한 query를 Internal Schema에 대한 query로 바꿈 → 이 행위를 Conceptual / Internal Mapping이라고 함.
    - 이후 Stored Database에 있는 Data를 요청된 query에 대한 처리를 하고, 다시 역순으로 사용자에게 되돌아 감.
    - DBMS는 이러한 흐름 전체를 총괄함.
- Independence가 어떻게 성립되는가?
    - 만약 전체 database에 대한 internal schema가 바뀐 경우

        → 만약 B tree 구조에서 Hash 구조로 바뀌었다면?

        1. Internal Level에서 Meta-Data만 바뀌면 되는 것임
        2. 즉, Conceptual Schema는 영향을 받지 않는다.

        → 질문 : Conceptual Schema가 변한다면 External에는 영향이 없나?

        1. Conceptual Schema가 변해도 관련한 meta-data만 바뀌기 때문에 External에는 영향이 없다.
        2. External에 영향이 없기 때문에 당연히 External으로 만든 Program에도 영향이 없다.

#### Internal Level

![](../images/dbsystem_week3_11.png)

- 전체 Database에 대한 Physical Storage을 기술한 것 → Physical Model을 사용함.

#### Conceptual Level

![](../images/dbsystem_week3_12.png)

- 사용자를 위한 전체 database에 대한 logical structure에 대해 기술한 것.
- 물리적인 저장소 구조에 대한 detail을 감춤
- 이를 위해 Physical 보다 상위 model인 conceptual / representational model을 사용한다.

#### External or View Level

![](../images/dbsystem_week3_13.png)

- Database의 일부분을 표현함
- **사용자가 필요로 하는 부분만 표현함** → 나머지 부분은 감춘다.
- 이를 위해 상위 model을 필요로 함. → conceptual / representational model → conceptual에 mapping 됨.

→ 각 level들과 model들이 헷갈림

Level

→ Internal / Conceptual / External or View

Model

→ Physical / Conceptual / Representational

#### Internal 과 External의 database 표현 방식의 차이

![](../images/dbsystem_week3_14.png)

- Internal Schema → Physical storage 내에 저장된 database를 표현한 것(물리적으로 어떻게 저장되어 있는가)
- External Schema → Logical / Conceptual한 database가 저장되어 있다.

![](../images/dbsystem_week3_15.png)

2. External → Conceptual

#### Data Independence

![](../images/dbsystem_week3_16.png)

- Database System에서 특정 level의 Schema를 변경할 수 있다.
- 단, 변경해도 상위 Level에 영향이 가지 않는다.(하위 Level은 영향이 갈 수 있다.)
- Logical / Physical Data Independence

#### Logical Data Independence

![](../images/dbsystem_week3_17.png)

- Conceptual Schema에 수정이 있을 때

    → External Schema에 영향이 가지 않는다.

    → 존재하던 application program(external을 기반으로 생성한)을 수정할 필요가 없다.

#### Physical Data Independence

![](../images/dbsystem_week3_18.png)

- Internal Schema에 수정이 있을 때

    → Conceptual / External / Application Program에 영향이 가지 않는다.

![](../images/dbsystem_week3_19.png)

- DBMS를 사용할 때 얻을 수 있는 가장 큰 장점 중 하나다.
- 즉, 최신화와 같은 수정이 용이하다.

#### DBMS Languages(Database Languages)

![](../images/dbsystem_week3_20.png)

![](../images/dbsystem_week3_21.png)

- DBMS가 제공하는 언어 → DBMS는 이것만 이해할 수 있기 때문.
- 이 언어를 사용해서 DB를 제어 및 관리할 수 있음
- DDL(Data Definition Language)
    - 다루고자 하는 target의 골격을 정의 및 수정하는 언어.
- DML(Data Manipulation Langauge)
    - 구조 내의 사용자 data를 검색 / 삽입 / 제거 / 수정 등을 하는데 사용되는 언어.
- SDL(Storage Definition Language)
    - Target DB 구조의 물리적인 구조(internal schema)를 나타내는 언어
- VDL(View Definition Language)
    - Target DB의 conceptual schema를 나타내는 언어

#### Procedural vs Non-procedural

![](../images/dbsystem_week3_22.png)

- Procedural DML
    1. 사용자의 질의(query)를 절차적으로 사용

        → 절차적이란? : step by step으로 디테일하게 처리할 순서를 정의한다는 의미

        **→ How to retrieve data**
    2. 누구에게 좋은가

        → 언어를 개발하는 개발자
- Non-procedural DML
    1. 사용자의 질의(query)를 선언적으로 사용

        → 선언적이란? : 사용자가 원하는게 무엇인지에 집중(순서를 정하지 않는다)

        **→ What(which) to retrieve**
    2. 누구에게 좋은가

        → 사용자 : 원하는 것만 이야기하면 가져옴

#### DBMS Interfaces

![](../images/dbsystem_week3_23.png)

![](../images/dbsystem_week3_24.png)

- SQL과 같은 언어를 사용하지 않고도 DBMS를 활용하기 위한 interface들
- Menu-based Interfaces
    - menu에서 제공하는 sample들을 활용해서 Data를 관리하는 방법
- Graphical User Interfaces
    - database를 access하는 것에 있어서 graphical한 database schema를 graphic 구조를 이용해서 표현하고 활용할 수 있도록 하는 interface
    - 보통 naive한 user를 위함 → 은행 ATM 화면 etc..
- Forms-based Interfaces
    - 어떠한 form을 주고 그 form을 채워서 원하는 DB에 access 할 수 있도록 하는 interface
- Natural Language Interfaces
    - 자연어를 활용해서 원하는 DB에 access할 수 있도록 하는 interface
- Intefaces for DBAs
    - DB 관리자를 위한 interface

#### DBMS Component Modules

![](../images/dbsystem_week3_25.png)

- 전체 DBMS 내에 어떤 component들이 존재하고 각각 어떤 역할을 하는가?
- Stored Database : 사용자의 data가 존재
- System Catalog / Data Dictionary :  Meta-Data가 존재(사용자의 data를 관리하기 위한)
- Stored Data Manager : 실제 Disk에 있는 Data를 직접적으로 가져옴
- Run Time Database Processor : Database 내에 있는 처리를 하게 되는 부분
- Concurrency Control / BackUp / Recovery Subsystems : 여러 사람이 동시에 사용할 때 문제가 생기지 않도록 하는 Component / 혹시모를 시스템 failure를 위한 Data를 다른 곳에 copy 해두는 것 / Failure 발생 시 backup 해둔 data를 활용해서 recovery
- Casual Users → Interactive Query → Query Compiler → Query Optimizer
    - Query Compiler → Query Optimizer

        → Query Compiler가 declarative language를 이해하고 그 방법 중 최적의 방법으로 Output을 내는 행위
- Application Programmers → Application Programs → ..
    - Application Programmers가 SQL을 사용해서 Application Program을 짜면 Precompiler가 전체 Program 중 SQL에 해당하는 내용만 골라냄.
    - 그 내용을 DML Compiler에게 전달하면 Query Optimizer를 통해서 최적의 무언가를 뽑아냄 → 그 결과를 Compiled Transactions에 전달.
    - 동시에 SQL을 제외한 나머지 코드들은 Host Language Compiler에게 전달.

→ 그냥 흐름이 이렇다 정도로만 이해하고 넘어가자

#### DBMS Component Modules

![](../images/dbsystem_week3_26.png)

![](../images/dbsystem_week3_27.png)

- Stored Data Manager
    - Storage에 저장되어 있는 전체 Data를 access하는 부분
- DDL Compiler
    - Schema를 다루는 language compiler
    - DDL에 의해서 정의된 schema를 처리해주는 compiler
    - 처리를 끝내면 meta-data 형태로 결과가 나오는데 그것을 system catalog에 저장
- Runtime Database Processor
    - 사용자의 Query를 처리하게 위해서 database에 access하는 부분
- Query Compiler(interactive SQL → 사용자가 던진 Query)
    - Interactive SQL을 parsing 하는 것. → parsing해서 내부적으로 DBMS가 이해할 수 있는 형태로 변경한다.
    - High Level Language인 SQL Statement를 Low Level의 Function Call로 바꿔주는 역할을 함
- Precompiler
    - 전체 프로그램 중 SQL로 짜여져 있는 statement를 골라내는 역할을 함.
- DML Compiler
    - Precompiler에서 골라진 statement를 받아서 하위 단계의 function call로 바꿔주는 역할을 함.

#### Database System Utilities

![](../images/dbsystem_week3_28.png)

![](../images/dbsystem_week3_29.png)

![](../images/dbsystem_week3_30.png)

- Database Utilities

    → DBA가 DB를 쉽게 관리할 수 있도록 해주는 Utility
- Loading

    → DBMS의 외부에 data file이 있을 때 사용자가 그것을 옮길 때 쉽게 옮길 수 있도록 도와줌.

- Backup

    → 한 시점의 database의 상태를 copy 해둔다.

    → Failure 발생 시 가장 최신의 backup 상태를 불러옴.
- Database Storage Reorganization

    → Database Files를 다른 방식의 구조로 바꿔주는 것.

    왜 바꿈? → 구조에 따라 성능이 결정되기 때문에 최적화 및 성능 개선 등의 목적

    → 주로, DBMS 성능 문제 해소를 위해 사용됨
- Performance Monitoring

    → DBMS의 성능을 모니터링 해줌.

    → DBA에게 제공함으로서 decision을 내리는데 도움을 줌.

#### Classification of DBMS

![](../images/dbsystem_week3_31.png)

- Data model을 기준으로 DBMS를 분류함.(하나의 DBMS는 하나의 data model을 가지기 때문)
    - Relational Model → 가장 많이 사용됨
        1. Database가 table들의 집합이라는 것.
        2. 각각의 table은 record라는 정보의 집합으로 표현
    - Network Model
        1. Data를 record type이라는 것으로 modeling함
    - Hierarchical Model
        1. Data를 계층적인 tree 구조로 표현
    - Object Model
        1. Database는 class들의 집합이라고 보고 표현.
        2. Data는 어떤 특정한 class에 속하는 object로 본다.
        3. 복잡한 data를 modeling 할 때 용이
