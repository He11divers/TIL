#### Relational Database Design by ER-to-Relational Mapping

![](../images/20261006_dbsystem_week5_2_03.png)

- Conceptual Design의 결과(Conceptual Schema = ER Model)을 가지고 Relational Design을 하는 방법을 배울 것

#### Mapping of “Regular” Entity Types

![](../images/20261006_dbsystem_week5_2_04.png)

- Entity Type은 무엇으로 매핑되는가? → 일단 Entity Type은 Regular & Weak가있다. 여기서는 Regular 먼저.
- Regular Entity Type을 하나의 relation으로 매핑해주는 것.
    - Entity Relations라고 부름.
    - Relationship type이 relation으로 바뀌는 경우는 Relationship relation이라고 부름.
- Attributes
    - 원래 있었던 attribute를 새로 만들어진 Entity Relation의 attribute로 바꾼다.
    - 즉, entity type의 모든 심플한 attribute들을 relation의 attribute로 바꿈.
    - “심플한 attribute”기 때문에 multivalued, composite의 경우에는 다른 방법을 사용함.
- Primary Key
    - Entity Type의 Key attribute 중 하나를 그냥 고르면 됨.

#### Mapping of “Weak” Entity Types

![](../images/20261006_dbsystem_week5_2_05.png)

- Regular와 동이랗게 entity relation 진행
- Attriutes
    - Weak Entity Type의 simple한 attribute를 새로 만든 relation에 넣음
    - Weak Entity Type은 혼자서 key를 생성할 수 없기 때문에 owner entity가 있다 → Owner의 primary key attribute을 새로 만들어진 relation에 가져와서 foreign key로 둠.
- Primary Key
    - Weak Entity Type의 partial key 중 하나를 고름
    - 그것과 foreign key를 합쳐서 primary key로 만듦.

#### Mapping of Multivalued Attribute

![](../images/20261006_dbsystem_week5_2_06.png)

- Multivalued Attribute → ER Model에서 2개 이상의 value를 가지는 attribute
- Relational Model에서는 attribute이 2개 이상의 value를 가지는 것을 허용하지 않음. → 그대로 relation 할 수 없음.
- 그럼? → Multivalued Attribute 자체를 하나의 새로운 relation으로 만든다.
- Attributes
    - Multivalued attributes가 새로운 relation의 attribute이 된다.
    - 새로운 relation의 key는?  
      → 원래 Multivalued attributes를 attribute로 가지고 있었던 entity type에 해당되는 relation.   
      → 그것의 key attribute를 새로운 relation의 attribute로 가져옴.  
      → 그것을 FK로 둠.

- Primary Key
    - 가져온 multivalued attributes의 attribute와 FK를 합쳐서 설정.

> ER Schema에 Multivalued Attribute가 있을 때 그것을 별도의 relation으로 만든다.  
> 새로 만들어진 Relation에는 Multivalued attribute를 구성하고 있던 attribute와 Multivalued attribute을 가지고 있던 entity type과 대응되던 entity type의 key attribute를 가져와서 FK로 둔다.

#### Mapping of Composite Attributes

→ 방법 1

![](../images/20261006_dbsystem_week5_2_07.png)

- Composite Attribute : 하나의 attribute이 여러 개의 sub attribute들로 구성되어 있는 attribute
- Composite Attribute를 별도의 relation으로 만든다.
- Attributes
    - 원래 ER Model의 Composite Attribute의 Component attribute의 simple attributes
    - 원래 Composite Attribute이 소속되어 있던 entity type이 relation으로 변한 것의 Primary key attribute을 가져와서 FK로 둔다.
- Primary Key
    - 가져온 FK를 PK로 둠.

→ 방법 2

![](../images/20261006_dbsystem_week5_2_08.png)

- Composite Attribute에 component attribute 들을 entity relation의 attribute으로 박아 넣음.

#### Mapping of Binary 1 : 1 Relationship Types

→ Relationship type의 mapping

→ Cardinality Ratio에 따라 다르게 mapping 함.

Cardinality Ratio가 1 : 1인 경우

- 별도의 relation 또는 table을 만들지 않음.

![](../images/20261006_dbsystem_week5_2_09.png)

1. Relationship type에 참여하는 2개의 entity type을 찾는다.  
   (1 : 1이니까 가운데 relationship type을 기준으로 양 옆에 있겠지)  
   그 후 각 entity type에 대응되는 relation을 찾는다.

2. 2개의 relation 중 하나를 선택  
   → 선택되지 않은 relation의 PK를 가져와서 선택된 relation의 FK로 설정

    → 2개의 relation 중 하나를 고를 때 total participation을 고르는게 더 유리함.

3. 원래 Relationship type에 속했던 simple attribute들을 선택한 relation으로 넣는다.

Cardinality Ratio가 1 : N인 경우

![](../images/20261006_dbsystem_week5_2_10.png)

1. Relationship type의 N쪽 사이드에 있는 entity type과 대응되는 relation을 찾는다.  
   ex) EMPLOYEE ↔ DEPARTMENT의 1 : N 관계 중 EMPLOYEE를 말하는것.

2. N 쪽 relation에 반대쪽 entity type의 PK를 가져와서 FK로 둔다.
3. 원래 relationship type에 속했던 attribute는 N 쪽 relation으로 가져온다.
- 근데 1 쪽 relation에 N쪽 PK를 가져오면 안되나??

    → DEPARTMENT에 EMPLOYEE의 PK를 가져온다는 소리인데.

    → EMPLOYEE의 SSN을 DEPARTMENT의 FK로 가져온다는 오면, 어떤 DEPARTMENT에 어떤 EMPLOYEE가 일한다   
    → relation을 표현하는 포인터 역할을 하긴 함.   
    → BUT DEPARTMENT에 일하는 사람은 여러 명이라 multivalued attribute가 되어야 하기 때문에 안됨.

Cardinality Ratio가 M : N인 경우

![](../images/20261006_dbsystem_week5_2_11.png)

- WORKS_ON → 하나의 EMPLOYEE도 여러 PROJECT에서 일할 수 있고, 하나의 PROJECT에도 여러 EMPLOYEE가 속할 수 있는 상황

    → 앞선 상황들과 다르게 한쪽의 PK를 FK로 가져오는 방법으로 해결할 수 없음.

- M : N relationship type과 대응되는 하나의 독립적인 relation을 만들어야 함.  
  → 예를 들어 105번 사원이 3번,4번 project에 속해 있다.  
  → relation에는 105 - 3, 105 - 4 이렇게 2개의 tuple이 생성됨.

- Attributes
    - 참여하는 2개의 entity type에 대응되는 2개의 relation에 PK를 각각 FK로 가져온다.
    - 원래 relationship type에 속했던 simple attribute도 이 relation에 투입
- Primary Key
    - 2개의 FK를 합친 것을 PK로 둔다.

#### Mapping of N-ary Relationship Types

→ binary M : N과 같은 방식으로 mapping

![](../images/20261006_dbsystem_week5_2_12.png)

1. 독립적인 Relation을 만든다.
2. 그 Relation에 속하는 attribute로서 참여하는 entity type들의 PK를 모두 FK로 가져옴(N개가 참여하면 N개) + relationship type에 존재하던 simple attribute도 가져옴
3. 가져온 N개의 FK를 합친 것을 PK로 둔다.

#### Company Database에 대해서 ER-to-Relational Mapping 해보자

![](../images/20261006_dbsystem_week5_2_13.png)

- Mapping of regular entity types

    ![](../images/20261006_dbsystem_week5_2_14.png)

    1. EMPLOYEE
    - EMPLOYEE ← Relation 하나 생성
    - 포함되어 있던 simple attribute를 포함
    - SSN을 PK로 유지

    ![](../images/20261006_dbsystem_week5_2_15.png)

    1. DEPARTMENT
    - DEPARTMENT ← Relation 하나 생성
    - simple attribute 포함시킴
    - Dname 과 Dnumber 중 하나를 골라 PK 설정 ← 사진의 경우 Dnumber

    ![](../images/20261006_dbsystem_week5_2_16.png)

    1. PROJECT
    - Regular니까 동일
    - attribute의 이름을 조금씩 바꾸는 이유 → 각 relation끼리 attribute_name이 겹치지 않게 하기 위함.

    ![](../images/20261006_dbsystem_week5_2_17.png)

    1. DEPENDENT
    - Weak entity type
    - DEPENDENT ← relation 생성
    - simple attributes 이름 바꿔서 포함
    - owner entity type(EMPLOYEE)의 PK를 FK로 가져온다.
    - PK는 FK + 원래 weak entity type의 partial key를 합쳐서 설정.

    ![](../images/20261006_dbsystem_week5_2_18.png)

    1. multivalued attributes → DEPARTMENT 중 Locations
    - DEPT_LOCATIONS ← relation 생성
    - DEPARTMENT(얘는 relation)의 PK를 FK로 설정
    - multivalued attributes 였던 Locations를 Dlocation으로 이명 후 attribute로 설정  
      → 기존 multivalued 였던 것이 여러 Tuple로 나눠서 표현됨

    - PK는 FK와 multivalued attributes였던 attribute를 합쳐서 설정

    ![](../images/20261006_dbsystem_week5_2_19.png)

    1. composite attributes → EMPLOYEE 중 Name(First, Middle, Last etc..)
    - EMPLOYEE라는 table에 Name이 아니라 Fname, Minit, Lname 3개의 component 들을 attribute로 집어 넣는다.

    ![](../images/20261006_dbsystem_week5_2_20.png)

    1. 1 : 1 Ratio의 binary relationship type → MANAGES
    - 각각 대응되는 relation이 이미 만들어져 있을 것임.
    - EMPLOYEE와DEPARTMENT 중 total participation인 DEPARTMENT 선택.
    - EMPLOYEE의 PK를 DEPARTMENT의 FK로 가져옴.
    - MANAGES의 simple attributes인 start_date도 attribute로 가져옴

    ![](../images/20261006_dbsystem_week5_2_21.png)

    1. 1 : N Ratio의 binary relationship type → WORKS_FOR
    - N쪽 entity type인 EMPLOYEE를 선택
    - 반대쪽 DEPARTMENT의 PK를 EMPLOYEE의 FK로 설정.

    ![](../images/20261006_dbsystem_week5_2_22.png)

    1. 1 : N Ratio의 binary relationship type → CONTROLS
    - N쪽 entity type인 PROJECT를 선택
    - 반대쪽 DEPARTMENT의 PK에서 이름을 살짝 바꿔서 FK로 설정.

    ![](../images/20261006_dbsystem_week5_2_23.png)

    1. 1 : N Ratio의 binary relationship type → SUPERVISION
    - EMPLOYEE가 각각 Supervisor와 Supervisee로서 참여함
    - EMPLOYEE(Supervisor)의 PK를 EMPLOYEE(Supervisee)의 FK로 가져옴.

    ![](../images/20261006_dbsystem_week5_2_24.png)

    1. M : N Ratio의 binary relationship type → WORKS_ON
    - 새로운 relation인 WORKS_ON 생성
    - EMPLOYEE의 PK인 Ssn과 PROJECT의 PK인 Pnumber를 이름 조금 바꿔서 FK로 가져옴.
    - WORKS_ON의 simple attributes인 Hours 포함.
    - PK는 2 FK를 합친 것으로 설정.

    #### 결과

    ![](../images/20261006_dbsystem_week5_2_25.png)

    - DEPARTMENT에 있던 Location(multivalued attribute) → DEPT_LOCATIONS로 이동
    - DEPENDENT는 Weak Entity type이었기 때문에 Owner인 EMPLOYEE의 PK를 가져옴
    - M : N 이었던 WORKS_ON → 별도의 table을 만듦.
    - ER Schema를 가지고 그릴 수 있어야함.
    - 이 그림을 보고 구조를 이해할 수 있어야함.
