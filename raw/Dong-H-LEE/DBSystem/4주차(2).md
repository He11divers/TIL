#### Constraints on Relationship Types

→ Relationship instance : 하나의 Entity instance와 또 다른 Entity instance 간의 관계를 표현한 것

→ Relationship Type : 그러한 Relationship instance들이 모여있을 때 같은 형식의 relationship instance들을 abstact 하게 표현한 것

![](../images/dbsystem_week4_part2_03.png)

- **Relationship type의 이름은 entity type과 다르게 동사로 지음**
- 여기서 다루는 constraint 들은 binary relationship에 해당되는 것임
- Cardinality Ration Constraint
    - 하나의 entity가 참여할 수 있는(가질 수 있는) relationship instance들의 최대 수
    - 하나의 instance가 최대 몇개의 relationship instance에 참여할 수 있는가를 표현하기 위함
    - 3가지 종류가 있음 → binary니까 entity type 2개가 참여
        1. 1 : 1 → 각 instance들은 각각 1 ㄷ 1로만 관계를 맺을 수 있다. → 관계가 없을 수도 있음 ex) 결혼
        2. 1 : N → 한 쪽의 instance가 다른 쪽의 여러 놈과 관계를 맺을 수 있다. → 관계가 없을 수도 있음  
           ex ) 지도교수 - 학생 관계
        3. M : N → 양쪽 모두 여러 놈과 관계를 맺을 수 있다. → 관계가 없을 수도 있음.

#### 1:1 Cardinality Ratio

![](../images/dbsystem_week4_part2_04.png)

- 하나의 EMPLOYEE는 하나의 DEPARTMENT에만 속할 수 있다.
- 각 DEPARTMENT는 하나의 EMPLOYEE한테만 MANAGE 받을 수 있다.

#### 1:N Cardinality Ratio

![](../images/dbsystem_week4_part2_05.png)

- 하나의 EMPLOYEE는 하나의 DEPARTMENT에서만 일함
- 하나의 DEPARTMENT는 여러 EMPLOYEE가 속할 수 있음

#### M:N Cardinality Ratio

![](../images/dbsystem_week4_part2_06.png)

- 하나의 EMPLOYEE가 여러 PROJECT에서 활동할 수 있음
- 하나의 PROJECT에는 여러 EMPLOYEE가 속할 수 있음

#### Constraints on Relationship Types

![](../images/dbsystem_week4_part2_07.png)

![](../images/dbsystem_week4_part2_08.png)

- Participation Constraint
    - 어떤 entity의 존재가 다른 entity와의 연관됨에 종속된다.
    - entity가 존재한다면 반드시 다른 entity와 연관이 있는지 없는지에 대한 내용
- Total Participation Constraint
    - 하나의 entity가 존재한다면 반드시 하나 이상의 다른 entity와 관계가 있어야함
    - ex) DEPARTMENT
- Partial Participation Constraint
    - 반드시 관계가 있지 않아도 됨
    - ex) EMPLOYEE

#### Attributes of Relationship Types

→ Attribute : 특정한 entity를 describe 하는 property

![](../images/dbsystem_week4_part2_09.png)

- Relationship type에는 attribute가 주어질 수도, 주어지지 않을 수도 있다.
- 주어지는 경우
    - relationship type에 참여하는 entity의 조합에 의해서 어떤 특성이 부여될 때
    - 각각의 relationship instance의 특징을 표현하는 것
    - attribute이 relationship type에 참여하는 entity type의 attribute에는 적합하지 않을 때 부여됨
- Binary Relationship Type에서는 M:N의 경우에 적합함 → 1:1이나 1:N의 경우에는 relationship type이 아니라 한 쪽으로(N 쪽) attribute를 생성하여 해결할 수 있음.

#### Weak Entity Type

![](../images/dbsystem_week4_part2_13.png)

- entity type 내부에 key attribute이 없는 것
- 내부에 있는 attribute 만으로는 key가 형성될 수 없는 entity type
- ex) DEPENDENT
    - DependentName, BirthDate, Sex, Relationship 만으로는 key를 생성할 수 없음

![](../images/dbsystem_week4_part2_14.png)

- Identifying Owner
    - Weak entity type에 entity들을 구분하는데에 사용하는 entity type이 identifying owenr

![](../images/dbsystem_week4_part2_15.png)

- Identifying Relationship Type
    - Weak entity type과 identifying owner를 엮어주는 relationship type
    - Weak entity type은 반드시 total participation constraint
    - 즉, 각 entity는 반드시 하나 이상의 entity와 관계를 가지고 있어야함

![](../images/dbsystem_week4_part2_16.png)

- Partial Key
    - identifying owner에 해당되는 한 entity와 여러 weak entity가 관계를 맺고 있을 때, 관계를 맺고 있는 weak entity들을 식별할 수 있는 attribute들의 집합
    - ex) DEPENDENT → 홍꺽정과 관계를 맺는 여러 부양가족이 있을 때, 전체 dependent에서 홍꺽정의 부양가족들만 뽑을 수 있는 **partial key : DependentName**

#### Refining Conceptual Design for the COMPANY Database

![](../images/dbsystem_week4_part2_17.png)

- 위 사진은 이전 강의에서 진행한 initial conceptual desgin임.
- Entity와 Attribute를 가지고 진행한 것.
- 이걸 이제 relationship type을 가지고 develop할 것.
- E-R model은 entity와 relationship으로 구성, entity와 relationship의 특징을 나타내는 attribute가 양쪽에 달라 붙을 수 있다.
- COMPANY Database에 대한 conceptual design을 relationship을 활용해 마무리 하자
    - 사진에 파란색으로 표시된 attribute가 있음 → ex) Manager → 사실 하나의 attribute가 아니라 EMPLOYEE와 연결되는 하나의 relationship으로  표현되는 정보임
- MANAGES

    ![](../images/dbsystem_week4_part2_18.png)

    - EMPLOYEE와 DEPARTMENT와의 1:1 관계를 나타내는 relationship type
    - entity type의 이름 → 명사 / relationship type의 이름 → 동사
    - Participation Constratins
        1. EMPLOYEE는 모두가 MANAGES에 참여할 필요 없음 → partial
        2. DEPARTMENY는 반드시 어떤 EMPLOYEE에 의해 MANAGES 되어야 함 → total
    - MgrStartDate → MANAGES라는 relationship type의 attribute → 어떤 EMPLOYEE가 DEPARTMENT를 언제부터 MANAGE 했는지 표현

        → MgrStartDate는 relationship type의 attribute지만 관계가 1:1이 아니라 1 : N인 경우 한 쪽의 entity type의 attribute로 들어갈 수도 있다. (복습할 때 예시 좀 확인해보자)
- WORKS_FOR(동사니까 relationship type)

    ![](../images/dbsystem_week4_part2_19.png)

    - 하나의 EMPLOYEE가 여러 DEPARTMENT에서 일할 수는 없지만 하나의 DEPARTMENT에는 여러 EMPLOYEE가 속할 수 있기 때문에 1 : N의 Cardinality를 가짐.
    - Participation Constraint → 양 쪽 모두 total
- CONTRLOS

    ![](../images/dbsystem_week4_part2_20.png)

    - 해당 PROJECT를 관리하고 있는 DEPARTMENT는 어디인가를 알려주는 relationship type
    - 하나의 DEPARTMENT가 여러 PROJECT를 CONTROL 할 수 있지만 하나의 PROJECT를 여러 DEPARTMETN가 CONTROL할 수 없기 때문에 1 : N의 cardinality를 가짐
    - 모든 PROJECT는 CONTROL하는 DEPARTMENT가 반드시 존재해야함 → total
    - 어떤 DEPARTMENT는 PROJECT를 CONTROL하지 않아도 됨. → partial
- SUPERVISION

    ![](../images/dbsystem_week4_part2_21.png)

    - 하나의 SUPERVISOR는 여러 SUPERVISEE를 둘 수 있지만 하나의 SUPERVISEE는 여러 SUPERVISOR를 둘 수 없음 → 1 : N
    - 양쪽 모두 필요충분관계가 아님 → partial
