#### INSERT Statement

![](../images/20261116_dbsystem_db10_03.png)

- table에 새로운 tuple을 추가할 때 사용하는 statement

  → table이 수정됨.

- 하나의 단일 tuple을 추가할 수 있음.
- 여러 개의 tuple들의 집합을 추가할 수 있음.

![](../images/20261116_dbsystem_db10_04.png)

→ 하나의 Tuple을 table에 집어 넣는 방법

- INSERT INTO \<table name> VALUES (\<list of attributes values>);
- list of attribute values의 순서는 추가하려는 table의 attribute 순서에 맞추어서 작성해야함.

![](../images/20261116_dbsystem_db10_05.png)

![](../images/20261116_dbsystem_db10_06.png)

- 하나의 tuple을 추가하되 모든 attribute value가 아닌 일부 attribute value만 추가하는 방식
- INSERT INTO \<table name>(\<list of attributes>)

  VALUES(\<list of attribute values>);
- \<list of attributes> 에는 추가할 attribute name들이 들어감.
- NULL이 허용되는 attribute 혹은 DEFAULT 값이 명시되어 있는 attribute는 \<list of attributes>에 없어도 됨.

  → 즉, NULL, DEFAULT가 허용 또는 명시되어 있지 않다면 반드시 포함되어야 함.  
  → 여기에 없는 attribute의 value는 NULL 혹은 DEFAULT 값이 채워짐.

![](../images/20261116_dbsystem_db10_07.png)

![](../images/20261116_dbsystem_db10_08.png)

- 여러 Tuple들을 한번에 INSERT하는 방법
- 추가되는 tuple들은 Query 문의 결과값으로 나온 tuple들임.
- INSERT INTO \<table name> (\<list of attributes>) \<select statement>;
- \<select statement>에 의해 가져오는 Tuple 들의 집합을 table에 INSERT 함.
- 단, \<list of attributes>의 수와 \<select statement>에 있는 attribute의 수는 같아야하며, 순서대로 대응되는 각각의 attribute type이 같아야함.

![](../images/20261116_dbsystem_db10_09.png)

![](../images/20261116_dbsystem_db10_10.png)

- 위의 예시로 만들어진 WORKS\_ON\_INFO는 최신화 되어 있지 않을 수 있음.
- base table의 변화를 자동으로 반영하기 위해 “view”라는 것을 활용함 → 이건 나중에 학습함.

#### DELETE Statement

![](../images/20261116_dbsystem_db10_11.png)

- table에서 tuple들을 지워내는 statement
- Delete 할 tuple을 찾아내기 위해 WHERE 절을 사용한다.
- 한번에 한 table 내의 tuple만 처리한다.

![](../images/20261116_dbsystem_db10_12.png)

- DELETE FROM \<table name> WHERE \<condition>; 의 형태
- 만약, WHERE 절이 없다면 table에 존재하는 모든 tuple이 지워짐.
- 단, table이 지워지는게 아님!!

![](../images/20261116_dbsystem_db10_13.png)

#### UPDATE Statement

![](../images/20261116_dbsystem_db10_14.png)

- 어떤 조건을 만족하는 tuple들에 대해서 어떠한 attribute value를 원하는 값으로 변경하고 싶을 때 사용하는 statement
- table instance를 변경하는 것.
- WHERE 절을 활용하여 원하는 조건을 만족하는 tuple의 instance를 수정함.
- 한번에 하나의 table에 대해서 적용.
- SET 절을 활용해서 어떤 attribute value를 어떠한 값으로 바꾼다고 명시할 수 있음.

![](../images/20261116_dbsystem_db10_15.png)

- UPDATE \<table name> SET \<list of ‘attribute = value’ pairs>

  WHERE \<condition>;

- ‘attribute = value’ 에서 attribute는 attribute name이고 value는 바꾸고자 하는 value임.
- 단, 여기서 WHERE 절은 없어도 됨. → WHERE이 없으면 그냥 해당 table의 모든 tuple에 대해서 수정한다고 보면 됨.

![](../images/20261116_dbsystem_db10_16.png)

- PROJECT table에서 Pnumber가 10번이 tuple 들의 Plocation을 ‘Bellaire’ Dnum을 5로 바꿔라.

![](../images/20261116_dbsystem_db10_17.png)

- EMPLOYEE table 에서 Dno가 5번인 tuple들에 대한 Salary를 1.1배 해서 저장해라.

#### Views

![](../images/20261116_dbsystem_db10_18.png)

- View는 하나의 table임. 근데 이제 다른 table로 부터 derived된 table.
- 가상 table로 여겨짐.
- 여러 테이블에서 파생해서 view를 가져올 수 있다. 단, view는 single table임.

![](../images/20261116_dbsystem_db10_19.png)

- View는 physical form으로서 존재할 필요가 없음. → 존재하지 않은 View에 대해서 update를 필요로 할 때 의도와 다르게 update가 진행되지 않을 수 있다.
- View는 view를 선언할 때(정의할 때) 만들어지는 것이 아닌 누군가가 View라는 table에 누군가가 Query를 던졌을 때
- View에 대한 Query는 일반적인 Physical Table과 비교했을 때 제한되는 부분(제약)이 없음.

#### Creating Views

![](../images/20261116_dbsystem_db10_20.png)

- CREATE VIEW \<view name> AS \<select statement>
- \<select statement>를 통해서 가져온 결과를 \<view name>의 이름을 가진 view에 가져온다.
- “주의” : 정의하는 시점에 \<select statement>를 수행 후 가져와서 view에 저장하는 것이 아님  
  → 정의 시점에 가져오지 않기 때문에 \<view name>이 물리적으로 존재하지 않음.  
  → 이렇게 정의된 view에 대해서 Query를 던지면 그때 생성됨.
- attribute name은 특별한 명시가 없다면 \<select statement>에 있는 attribute name을 그대로 사용함.

![](../images/20261116_dbsystem_db10_21.png)

![](../images/20261116_dbsystem_db10_22.png)

- 2가지 예시 모두 View가 물리적으로 생성된 상태가 아님. → select statement 조차도 수행되지 않은 상태.
- V2에선느 SELECT 절에 attribute name이 명시되지 않았기 때문에 CREATE VIEW 절에서 view에서 보여줄 attribute name을 명시해야함.

#### Querying Views

![](../images/20261116_dbsystem_db10_23.png)

- Query문은 일반 table과 동일
- FROM 절에 WORKS\_ON1이라는 view가 명시되어 있기 때문에 이 순간 view와 관련된 select statement를 처리 후 조건에 만족하는 tuple을 채워넣음.

![](../images/20261116_dbsystem_db10_24.png)

- WORKS\_ON1이라는 view가 없었다면 Query는 이 슬라이드가 되었을 것.
- 확실히 김 → view를 한번만 정의해둔다면 많은 사람들이 편리하게 공유할 수 있음.

![](../images/20261116_dbsystem_db10_25.png)

- View를 사용했을 때의 장점
  - 특정 Query문이 간단해짐.
  - 보안 및 권한의 관리에 유용함 → Private table의 일부분만 공개하고 싶을 때 view를 만들어 일부분만 공개하고 private table은 비공개로 둘 수 있음.
  - 항상 최신 정보를 가지고 있음.  
    → view 라는 table에 query를 던진 시점에서 그때 base table에 있는 내용을 참조해서 가져오기 때문에 view는 항상 up-to-date한 정보를 가지고 있음.  
    → update가 먼저 처리되고 view가 만들어진다.

![](../images/20261116_dbsystem_db10_26.png)

- View를 사용했을 때의 단점
  - 성능과 관련된 단점이 있음.

    → update 상황에서 view를 사용하지 않는다면 INSERT/DELETE/UPDATE 등에서 base table에서 가져와서 그냥 tuple을 처리하면 됨.

    → 하지만 view로 제공되는 경우에는 Query를 처리하기 전에 base table로 새로 가져와서 query 처리 후 view에 update 해야함.

  - Update 면에서 제약이 있음.

    → view에 대해서 update가 필요로 할 때 view는 자신만의 tuple이 있는 것이 아니기 때문에 base table에 접근해서 update 해야함. 하지만 이런 것들이 적절하지 않은 case가 있음.

![](../images/20261116_dbsystem_db10_28.png)

- View는 직접적으로 update 할 수 없음. → View가 기반으로 두고 있는 base table의 내용이 update 된다는 의미.
- 하지만 항상 가능하지는 않고 일부 View에 대해서만 가능함.
- Update가 안되는 경우? → View를 update하는 것이 정확히 뭘 update하는 지에 대해 모호한 경우

![](../images/20261116_dbsystem_db10_29.png)

- John Smith라는 이름을 가진 사람이 참여한 project의 이름을 ProductY로 바꾸고 싶다.
- UPDATE 할 대상은 table인지 view인지 모르고 요청

![](../images/20261116_dbsystem_db10_30.png)

- 이전 슬라이드의 view에 대한 UPDATE statement에 대한 하나의 접근

  → project 이름 자체가 바뀐 것.

- WORKS\_ON1은 table이 아니라 view이기 때문에 우선 관련된 PROJECT table(base table)에서 조건에 맞는 tuple을 찾고 수정함.

![](../images/20261116_dbsystem_db10_31.png)

- 이전 슬라이드의 view에 대한 UPDATE statement에 대한 또 다른 접근 → 하나의 statement에서 여러 해석이 가능하다는 의미  
  → John Smith라는 사람이 참여하는 project가 바뀐 것.

#### Indexes

![](../images/20261116_dbsystem_db10_34.png)

- 어떤 Query를 던졌을 때 빠르게 결과를 보기 위한 일종의 meta-data

  → B-Trees의 구조를 가지고 있음.

  → 그냥 단순하게 SELECT Query를 빠르게 해주는 것이라고 이해해도 무방.

- Indexing Attributes → index를 attribute에 build 한다?
- 만약 index attribute이 select query의 where 절에 존재한다면 Query의 속도가 매우 빨라짐
- Atrribute가 N개 라면 index도 N개가 만들어짐 → N이 매우 크다면 많은 공간이 요구됨.

  → 때문에 꼭 필요한 위치에서만 index를 세팅하도록 권장함.

#### CREATING Indexes

![](../images/20261116_dbsystem_db10_35.png)

- CREATE INDEX \<index name> ON \<table name> (\<list of attributes>);
- \<table name>의 \<list of attributes>에 대한 index를 생성하라는 의미.

![](../images/20261116_dbsystem_db10_36.png)

![](../images/20261116_dbsystem_db10_37.png)

- Index를 build할 때 attribute value의 순서를 지정할 수 있음.
- Default는 ASC(오름차순)임.
- DESC 키워드 활용해서 내림차순 설정 가능.

![](../images/20261116_dbsystem_db10_38.png)

![](../images/20261116_dbsystem_db10_39.png)

- 여러 attribute에 대해서 index를 설정할 수 있다.
- 여러 attribute에 대해서 Index를 설정한다면 여러 attribute에 대한 value들을 묶어서(concatenate) 하나의 value처럼 다루면서 index를 구성한다.

#### UNIQUE Keyword

![](../images/20261116_dbsystem_db10_40.png)

- CREATE UNIQUE INDEX SsnIndex ON EMPLOYEE(Ssn);
- 어떤 tuple이 들어왔을 때 indexing 단계에서 똑같은 값을 가지는 second tuple을 막는 것.

#### CLUSTER Keyword

![](../images/20261116_dbsystem_db10_41.png)

- Tuple들을 모아두는 것.
- 저장되는 공간 상에서 모아두는 것.
- Index는 어떤 특정 attribute에 대해서 build하는 것임. → Cluster라는 keyword를 사용하면 index가 build 되는 그러한 attribute의 값이 같거나 비슷한 tuple들이 물리적으로 비슷한 위치에 저장됨.
- 새로운 tuple이 왔을 때 저장되는 위치는 그 tuple과 index가 build된 attribute의 값이 비슷한 녀석 근처로 간다는 소리.
- create 하는 index가 저장되는 record(tuple)의 위치를 결정하게 됨.
- join이나 범위 조건이 걸렸을 때 성능을 향상 시키는 장점이 있음.

![](../images/20261116_dbsystem_db10_42.png)

- EMPLOYEE가 INDEX로 저장될 때 Dno가 비슷한 사람끼리 모여서 저장됨
